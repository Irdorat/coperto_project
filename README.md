# Прогноз потока гостей ресторана

## Общая информация
Проект для прогнозирования количества гостей ресторана на следующие семь дней по историческим данным.

Решение включает:

- исследовательский анализ данных;
- подготовку дневного временного ряда;
- генерацию календарных, лаговых и скользящих признаков;
- наивный сезонный baseline;
- сравнение Linear Regression с сезонным baseline и контрольными экспериментами Prophet и CatBoost;
- временную валидацию без перемешивания;
- сохранение итоговой модели;
- CLI-скрипт для построения семидневного прогноза;
- тесты на отсутствие утечки при генерации признаков.

## Постановка задачи

По истории посещаемости одной ресторанной точки необходимо спрогнозировать количество гостей на каждый из следующих семи дней.

Основной сценарий использования:

1. Подготовить дневной датасет.
2. Обучить итоговую модель.
3. Сохранить модель на диск.
4. Запустить predict.py, указав ресторан и дату начала прогноза.
5. Получить прогноз на горизонты D+1–D+7.

## Запуск проекта через Docker

Дата начала прогноза может быть любой датой после окончания исторических данных. Если между концом истории и запрошенной датой есть промежуток, модель рекурсивно прогнозирует недостающие дни и использует эти значения как историю. Качество модели подтверждено только для семидневного горизонта; дальний рекурсивный прогноз следует интерпретировать осторожно.

Для запуска проекта требуется только установленный Docker. Локальная установка Python и библиотек из requirements.txt для запуска прогноза не требуется.

Проверить установку Docker:

```bash
docker --version
```

### Сборка Docker-образа

Команду необходимо выполнять из корня проекта:

```bash
docker build -t restaurant-forecast:latest .
```

Во время сборки Docker:

1. создаёт окружение Python 3.11;
2. устанавливает зависимости из `requirements-runtime.txt`;
3. копирует код и подготовленный датасет;
4. запускает `train.py`;
5. сохраняет обученную модель внутри образа.

После изменения кода, данных или зависимостей образ необходимо пересобрать:

```bash
docker build --no-cache -t restaurant-forecast:latest .
```

## Данные:

Данные я взял из открытого источника, а именно с платформы Kaggle: https://www.kaggle.com/datasets/ahmedmohamed2003/restaurant-sales-dirty-data-for-cleaning-training/data (для удобства я оставил датасет в репозитории data/raw/)

Исходные данные содержат:

- Order ID - id заказа
- Customer ID - id гостя
- Category - категория позиции
- Item - наименование позиции
- Price - цена
- Quantity - количество
- Order Total - суимарный чек (price*quantity)
- Order Date - дата заказа (период с 2022-01-01 до 2023-12-31 (2 года))
- Payment Method - способ оплаты

Так как исходный датасет не содержит готовой целевой переменной количества гостей в день,
количество гостей за день определяется как число уникальных Customer ID

Исходный датасет также не содержит идентификатора ресторана, поэтому все записи рассматриваются как история одной точки с restaurant_id = 1.
После агрегации подготовленный дневной датасет содержит 730 наблюдений и находится в data/processed/daily.csv.
Его основные поля:
- restaurant_id — идентификатор ресторана;
- date — календарная дата;
- guests — число уникальных клиентов за день;
- revenue — известная часть дневной выручки;
- missing_sales_count — число заказов с неполными финансовыми данными;
- missing_ratio — доля таких заказов за день.

## Обработка данных

В исходных данных присутствуют пропуски в:

- Item
- Price
- Quantity
- Order Total
- Payment Method

Строки с пропусками не удалялись целиком, поскольку Customer ID
и Order Date остаются доступными и позволяют использовать наблюдение
для расчёта целевой переменной guests.

Для финансовых показателей дополнительно создавался индикатор наличия
пропущенных данных.

После дневной агрегации была проверена непрерывность календаря. В рассматриваемом периоде отсутствующих календарных дат не обнаружено.
Текущая реализация проверки календаря завершает работу с понятной ошибкой, если в обработанном ряду есть пропущенная дата. Для полноценного production-сценария необходимо дополнительно различать:
- закрытый день с нулём гостей;
- технический пропуск выгрузки;
- период, когда ресторан ещё не работал.

Потенциальные выбросы в guests определялись с помощью межквартильного размаха.
Найденные высокие значения дополнительно сравнивались с:
- количеством заказов;
- количеством проданных позиций;
- выручкой.
Аномальные значения посещаемости сопровождались изменениями связанных показателей, поэтому признаков технической ошибки обнаружено не было. Эти наблюдения сохранены: автоматическое удаление могло бы убрать реальные дни повышенного спроса.

## Признаки

Логика генерации признаков вынесена в src/features.py и переиспользуется при обучении и инференсе.

Для ML-моделей используются календарные признаки:

- day_of_week
- month
- is_weekend
- is_holiday
- days_since_start

Лаговые признаки:

- guests_lag_1
- guests_lag_7
- guests_lag_14
- guests_lag_28

Скользящие средние:

- guests_mean_7
- guests_mean_14
- guests_mean_28

Все rolling-признаки рассчитываются только по прошлым значениям:

shift(1).rolling(...)

Это предотвращает попадание текущего значения целевой переменной
в признаки модели.

## Валидация

Поскольку данные являются временным рядом, случайное перемешивание
не используется.

Данные разделяются хронологически:

TRAIN → TEST → VALIDATION

- train используется для обучения;
- test используется для сравнения моделей;
- validation остаётся нетронутым до выбора финальной модели.

Для оценки используется 7-дневный rolling backtest.

В каждой точке прогнозирования модель получает только историю,
доступную до начала прогнозируемой недели, и прогнозирует сразу: D+1, D+2, ..., D+7.

Фактические значения guests внутри прогнозируемой недели
не используются для построения признаков.

Для моделей с лаговыми признаками прогноз выполняется рекурсивно:
предсказание предыдущего дня используется при построении признаков
следующего дня.

Такой подход имитирует реальный сценарий, в котором в момент прогноза
фактическая посещаемость следующих семи дней неизвестна.

## Основные метрики качества:

- MAE = mean(|actual - prediction|)
- MAPE = mean(|actual - prediction| / actual) × 100%

Дополнительной метрикой оценки является время инференса модели

## Модели

В проекте сравниваются следующие подходы:

### Seasonal baseline

Прогноз равен количеству гостей в тот же день предыдущей недели:

prediction(t) = guests(t - 7)

### Linear Regression

Линейная регрессия используется вместе с StandardScaler
в scikit-learn Pipeline.

### Prophet

Используется как альтернативный подход к моделированию
временной сезонности.

### CatBoost

Градиентный бустинг сравнивается с Linear Regression
на тех же признаках и том же временном разбиении.


## Результаты на test

Все модели сравниваются на одном и том же test-периоде
и одинаковом 7-дневном горизонте.

| Model | MAE | MAPE | inference_time_sec, ms |
|---|---:|---:|---:|
| Prophet | 3.327| 16.86% | 0.39 |
| Linear Regression | 3.370 | 16.94% | 0.1  |
| CatBoost | 3.431 | 17.41%	 | 0.2 |
| Seasonal baseline | 4.619 | 23.61% | 0.03 |


Prophet показал минимальную MAE, но преимущество над Linear Regression составило около 0.04 гостя в день. С учётом близкого качества, простоты, скорости обучения и интерпретируемости итоговой моделью выбрана Linear Regression. В текущем подходе нет смысла в использовании более сложных моделей.

Linear Regression улучшила baseline:
- по MAE примерно на 27%;
- по MAPE примерно на 28%.

Финальная оценка на ранее не использовавшемся validation-периоде:

| Metric | Value |
|---|---:|
| MAE | 3.22 |
| MAPE | 15.99% |
| Среднее время финального инференса недели | 0.07 сек |

## Интерпретация модели

Наибольший вклад в прогноз Linear Regression вносят скользящие средние за 7 и 14 дней.
Модель в основном оценивает недавний уровень посещаемости и его изменение относительно более длинного периода. Коэффициенты лаговых и скользящих признаков следует интерпретировать осторожно, поскольку эти признаки коррелируют между собой.
Коэффициенты day_of_week, is_weekend и is_holiday сравнительно малы, что согласуется с результатами EDA: выраженного недельного и праздничного эффекта в данных не обнаружено.

## Анализ ошибок
Итоговая модель склонна возвращать прогноз к среднему уровню примерно 20–21 гость. Поэтому самые большие ошибки возникают в дни с необычно высокой или низкой посещаемостью.
Наибольшая ошибка validation-периода наблюдалась 25 ноября:
- фактическое значение - 34 гостя;
- прогноз - около 21 гостя;
- абсолютная ошибка - около 13 гостей.
Это показывает, что текущая модель подходит для оценки обычного уровня нагрузки, но хуже прогнозирует редкие всплески и провалы спроса.

## Бизнес-вывод

MAE 3.22 означает, что в среднем прогноз ошибается примерно на три гостя в день.
Такой прогноз может использоваться как ориентир для:
- планирования смен сотрудников;
- оценки базовой загрузки ресторана;
- планирования закупок продуктов с коротким сроком хранения;
- сравнения ожидаемого и фактического потока гостей.

## Ограничения решения
- Целевая переменная является приближением количества гостей, рассчитанным по уникальным Customer ID.
- В данных представлена только одна ресторанная точка.
- География ресторана неизвестна, поэтому выбор календаря США является предположением.
- Модель не использует погоду, акции, мероприятия, бронирования и другие внешние факторы.
- Linear Regression плохо предсказывает редкие резкие изменения посещаемости.
- MAPE может быть нестабильна при небольших фактических значениях.

## Что бы я доделал при наличии времени

- Добавил внешние признаки: погоду, акции, бронирования и локальные события.
-  Проверил решение на датасете с несколькими ресторанами и более выраженной сезонностью.
